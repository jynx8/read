How code becomes a product

Version control, environments, and the exact route from a developer's branch to something a customer runs. The organising principle is not speed — it is how long you have to change your mind.

TODAY

Everything that currently exists is a development environment. No customer has ever run Jynx. This document describes the route that is already decided, and marks honestly which parts are built.

The release track

Eight stages, one human gate

Read the left rail first. It is the whole design: each stage is labelled with how you undo it, and the gate sits exactly where undo stops being possible.

Instantdelete the branch

1 · Branch

Short-lived, off main, named after the work rather than the person — the number is its task. Two days is the target; a week is a smell.

git switch -c feat/13-prefix-css
Instantclose the request

2 · Pull request

Automated checks run on every push: repository rules, dependency direction, session records, lint, tests, build. A disposable preview deploys alongside, so the change can be looked at rather than imagined.

Minutesrevert the commit

3 · Merge to main

One trunk, always releasable. Unfinished work merges early behind a flag rather than living on a branch for a fortnight, because a branch that old is no longer the same codebase.

Instantleave it unmerged

4 · Version proposal

Each change carries a note saying what it affects and how significantly. Those notes accumulate into a proposed set of version numbers and a changelog, opened automatically as its own request. Nothing is decided yet.

The gatea person, on purpose

5 · A human approves the release

The only manual step in the entire route, and the last moment anything can be reconsidered. Merging the version proposal creates the tags, and everything after this point runs unattended.

It is manual for one reason, and it is not caution. Everything above this line can be undone in under a minute. The next line cannot be undone at all.

Neveronly a higher version

6 · Publish

The packages other companies install go out to the public registry, signed so anyone can verify which commit produced them. The artifact published here is the same one the tests ran against — never rebuilt, because a rebuild is a different artifact and the tests passed on something else.

A published version cannot be withdrawn. Removal is blocked after seventy-two hours and breaks everyone who installed it in the meantime. The only remedy for a bad release is a better one, at a higher number.

~1 minuteredeploy the last build

7 · Deploy

The hosted service and the website move to the new version. Both roll back by redeploying the previous build, which is why they need no gate of their own.

—a message, not an action

8 · Production reports back

Every release notifies the team, on their phones, saying what shipped and — the part that matters — whether it can be undone. This message is the only connection between production and everything the development side runs.

Environments

Three, and only three

There is deliberately no staging environment. It is added the first time a bad deploy would embarrass us in front of a customer — a staging server nobody looks at is a machine that lies to you about being tested.

EnvironmentExists whenTriggered by Holds real credentialsReachable by automation
local A developer's machine. Everything built so far lives here. Running the dev server development only full access
preview One per open pull request. Disposable, deleted on merge. Opening a pull request preview-scoped may deploy
production The published packages, the hosted service, the website. A human approving a release the real ones notification only

The last column is enforced by key custody, not by policy. Production credentials exist only where the release pipeline and the hosting providers keep them. A development environment cannot read them, so it cannot deploy, publish or roll back — not because it is forbidden to, but because it does not hold the keys. A rule that depends on software choosing to obey it is a wish.

The customer boundary

What ships, and what never leaves the building

Jynx runs inside the customer's own application. That makes this line the most important one in the architecture, and it is drawn by allowlist: everything is hidden unless it was deliberately opened.

What the customer gets

a declared allowlist
  • The interface itselfPoint at anything, say what you want, watch it happen.
  • Every piece of their own dataTheir comments, threads, history, results — all of it, exportable.
  • Their colours and themeJynx adapts to the product it sits inside.
  • Their agents, named as they likeNaming a teammate is part of trusting one.
  • Their settings and permissionsIncluding how much the system may do without asking.

What the customer never sees

not hidden — never sent
  • Readable source of the productNo maps back to original code in anything shipped.
  • Instructions given to the modelsThe wording is a large part of what makes it work.
  • Which models, and how work is routedThe choice of engine per task is the engineering.
  • Any credentialNothing that authenticates anything reaches a browser.
  • Internal failuresAn error gives a reference number, never a file path or a query.
  • Anyone else's anythingEvery request is re-checked against the tenant on the server.

The honest limit: anything sent to a browser can be read by whoever receives it, and obfuscation only raises the cost. So the answer is not to protect what is shipped — it is to ship nothing worth taking. The interface is the thin part; the judgement lives on the server, where it is reached through a contract rather than handed over.
